# 実行手順

## 0. 目的とスコープ

既存の Issue（ラフな依頼・メモ）を、**壁打ち（対話）**を通じて実装可能な要件へ具体化し、**その Issue の本文へ要件を書き戻す**。ここまでが本スキルのスコープ。

- **実装・コード変更・ブランチ作成はしない。**
- 定義が固まったら Issue に `要件定義済み` ラベルを付け、実装に入れる状態にする。

## 1. 手順

1. **対象 Issue を取得する**
   - `gh issue view <番号> --comments`（タイトル・本文・既存ラベル・コメントを確認）。
   - 取得したら、最初に「#番号 タイトル」を出力してから壁打ちに入る。
2. **文脈を掴む**（推測で進めない）
   - 関連する既存コード・`docs/issues/` の過去プランを確認し、矛盾があれば指摘する。
3. **課題を明確化する（問い返す）**
   - 「何を・なぜ・誰のために・成功条件は何か」を引き出す。
   - 前提・制約・スコープがあいまいなら、決めつけずに質問する（1 度に多く聞かず要点に絞る）。
4. **選択肢とトレードオフを出す**
   - 案を複数提示し、各案のメリット/デメリット・影響範囲を並べる。推奨は述べてよいが、**最終判断はユーザーに委ねる**。
5. **リスク・依存・未確定を洗い出す**
6. **合意できた範囲を本文フォーマットへ整形する**（下記）。未合意は「未確定事項」に残す。

## 2. Issue 本文のフォーマット

```markdown
## 課題 / 背景
## 目的（この Issue で達成したいこと）
## 受け入れ条件（Done の定義）
## 影響範囲（画面 / ルーティング / DB / 既存機能）
## 未確定事項・要確認
## 参考（docs / 関連 Issue / コード）
```

## 3. 本文への書き戻し・ラベル付与

1. 整形した本文をユーザーに見せて了承を得る。
2. 本文をファイルに書き出し、`gh issue edit <番号> --body-file <path>` で更新する。元の依頼メモは消さず、末尾の「参考」に残す。
3. **要件が固まったら** `gh issue edit <番号> --add-label 要件定義済み` を付与する。
   - ラベルが無ければ `gh label create 要件定義済み --color 0E8A16 --description "要件が固まり実装に入れる"` で作る。
   - **未確定事項が残る間はラベルを付けない。**
4. 変更点（更新した見出し・追加した受け入れ条件・付けたラベル）を要約して伝える。

## 4. 次工程

- スコープが大きい／設計が重い場合は [ghi-specifier](../ghi-specifier/SKILL.md) で `docs/issues/` にプラン化することを勧める。
- 実装は [ghi-resolver](../ghi-resolver/SKILL.md) で行う。
